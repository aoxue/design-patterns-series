### 2.2 V2 懒汉式（2:26–3:13）

| 镜号 | 台词 | 画面 | 代码切分 |
|---|---|---|---|
| 2.2 · 2:26–3:13 | 第二版，懒汉式：instance 先留空，第一次有人来拿再建。判空、创建、返回，单线程里跑，无懈可击。但码上购的接口是多线程的。线程 A 执行到判空，通过，还没来得及 new；线程 B 也判空，也通过。两个线程在 new 之前擦肩而过，各自创建一个实例。单例？只剩个名字。我们一夜回到事故现场：两个「自己」，两份缓存。最粗暴的修法：方法上加 synchronized，一次放行一个线程。能用，但 getInstance 是高频热路径，每次调用都要抢锁。为了一个只在第一次有意义的判空，付出一辈子的锁开销，不值。这个「既要懒、又要快、还要安全」的死结，就是第三版的舞台。 | diff 呈现（删红增绿）；切动画板 A1：两线程时序翻车，两个实例分叉画面配故障音；`synchronized` 方法版一闪而过，打「⚠ 每次抢锁」标签划掉 | **C3** diff（对 C2）＋ **A1** 动画板 |

### 2.3 V3 双检锁 DCL（3:13–4:26）★ 本期视觉亮点

| 镜号 | 台词 | 画面 | 代码切分 |
|---|---|---|---|
| 2.3a · 3:13–3:41 | 第三版，双检锁 DCL（Double Checked Locking）。结构上有个口诀：一查、加锁、二查、创建。进门先做一次无锁判空，99% 的请求到这里就被打发走了；只有发现实例还没建，才进 synchronized；进去之后必须再判一次空：等你拿到锁的时候，可能前一个线程刚建完。 | C4 四步依次标号浮现（一查→锁→二查→创建） | **C4** 全新出现 |
| 2.3b · 3:41–4:26 | 但这段代码真正的灵魂，是 instance 前面那个 volatile。这不是面试官为难你，是 JVM 真的会动手脚。new PromoConfigManager() 在 JVM 眼里是三步：一，分配内存；二，执行构造器初始化；三，把 instance 指向这块内存。编译器和 CPU 可能把后两步调换顺序：先指、后建。单线程无所谓，多线程下致命：线程 A 刚执行完「指向」还没「初始化」，线程 B 在外面一查，非空！高高兴兴拿走，一调方法，里面全是 null。这个 bug 复现概率极低，低到你复盘时怀疑人生。volatile 的作用一句话：禁止这个重排，保证别的线程要么看到 null，要么看到完整的对象。把这张时间轴图截下来，这是本期最值钱的一页。 | 切全屏动画：三块积木 ① 分配内存 ② 初始化 ③ 指向；②③积木交换位次 → 线程 B 拿到半成品爆炸特效；volatile 出现时积木焊死（铆钉音效） | ＋ **A2** 动画板 |

**C4 · V3 双检锁（10 行）**

```java
public class PromoConfigManager {
    private static volatile PromoConfigManager instance;      // volatile：防指令重排
    private PromoConfigManager() { refresh(); }
    public static PromoConfigManager getInstance() {
        if (instance == null) {                               // 一查：无锁，挡掉绝大多数
            synchronized (PromoConfigManager.class) {
                if (instance == null) {                       // 二查：拿到锁再确认
                    instance = new PromoConfigManager();
                }
            }
        }
        return instance;
    }
}
```

| 2.4 · 4:26–5:21 | 双检锁解决了安全和性能，但代码复杂度也上来了。有没有一种写法，既懒、又安全，还不用自己处理并发？有，第四版，静态内部类，手写单例里我最推荐的写法。getInstance 什么都不判，直接返回 Holder.INSTANCE；而 Holder 这个内部类，JVM 保证它第一次被用到才加载，这不就是懒加载吗；类的初始化过程 JVM 又天然加锁，这不就是线程安全吗。我们一行并发代码没写，懒和安全白送，连 volatile 都省了。不是我们聪明，是 JVM 的类加载机制早就替你把路修好了。不过它和前面三版一样，有扇门没锁死：构造器挡得住 new，挡不住反射。这扇门，留给压轴的第五版。 | C5 出现；JVM 图标在 Holder 类上挂两块牌子「用时才加载」「初始化自带锁」；底部对比条：DCL 10 行 vs 内部类 6 行 | **C5** 全新出现 |

## 5. 什么时候别用（9:18–10:39）

差异化核心段落，不许省略。

| 镜号 | 台词 | 画面 | 代码切分 |
|---|---|---|---|
| 5.1a · 9:18–9:39 | 每期最后，我们都会问同一个问题：什么时候别用。三条警告。第一，单例的本质是全局变量。类名一点，哪里都能 getInstance；依赖关系不体现在方法签名里，而是藏进代码暗处。今天爽，三个月后重构时，它从暗处给你一刀。 | 第一张警告卡压屏（⚠ 全局变量） | 无 |
| 5.1b · 9:39–10:20 | 第二，有状态单例是并发炸弹。今天五版代码防的是「只创建一次」；但实例里的可变字段，缓存的 Map、随手 set 的成员变量，并发读写照样出事。创建安全，不等于使用安全。为什么？单例只承诺「实例全系统只有一个」，从没承诺「这个实例里的数据可以随便并发访问」。拿缓存 Map 举例：线程 A 一查，没有，正要写。线程 B 也一查，也没有，也写。一边的结果，被另一边悄悄覆盖。HashMap 并发写，甚至会把内部结构写坏，整台服务卡死。所以解法不在单例模式里：要么换成 ConcurrentHashMap、给写路径加锁，要么干脆让单例无状态。 | 第二张警告卡压屏（⚠ 状态炸弹） | 无 |
| 5.1c · 10:20–10:39 | 第三，难测试。getInstance 写死在调用处，单测想塞个假实现进去？插不进。正解是依赖注入：实例从「自己全局去拿」变成「外面递进来」，这正是刚才 Spring 影子的深意。最后一个常见过度设计：无状态的工具类，一堆 static 方法就够，别硬套单例的壳。 | 第三张警告卡压屏（⚠ 难测试）＋第四张小卡「工具类 ≠ 单例」；画面渐暗只留中间待机位，为片尾金句蓄力 | 无 |
